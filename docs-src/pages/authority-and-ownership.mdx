# Authority & Ownership

Multiplayer engines that conflate "who created this thing" with "who's allowed to update this thing" end up with weird edge cases. Connection Engine splits them cleanly.

| Relation             | Target  | Transferable? | Meaning                                     |
|----------------------|---------|---------------|---------------------------------------------|
| `OwnedBy`            | User    | No            | Provenance. Who made this. Permanent.        |
| `AuthoritativeFor`   | Peer    | Yes           | Runtime authority. Who's allowed to update. |

A user can own many things across many sessions. A peer is one device — one engine instance — one browser tab. A user can have multiple live peers (desktop + phone); authority over a given entity is on exactly one of them at a time.

## `spawnPrefab` is the networked-entity factory

Owner + authority are wire concerns, so they're assigned by the network-layer factory, not by the base ECS primitive. `createEntity` is pure ECS (just allocates a bitECS entity); `spawnPrefab` composes the four things every networked entity needs:

```ts
import { spawnPrefab, getOwner, getAuthority } from '@connectionengine/core'

const e  = spawnPrefab(world, 'avatar:alice')                            // owner=localUser, authority=localPeer
const e2 = spawnPrefab(world, 'avatar:bob', { owner: bob })              // explicit owner; authority still defaults
const e3 = spawnPrefab(world, 'item:1',   { parent: container })         // child of an existing entity
```

Under the hood, `spawnPrefab(world, uid, { parent?, owner?, authority? })` does:

1. `createEntity(world)` — allocate the bitECS entity
2. `setUID(world, e, uid, { parent })` — give it a wire-addressable path
3. `addRelation(world, e, OwnedBy, owner ?? world.localUser)` — permanent provenance
4. `addRelation(world, e, AuthoritativeFor, authority ?? world.localPeer)` — runtime authority

Every networked entity has an owner. `spawnPrefab` throws if no owner can be determined. The first thing your runtime does is bootstrap `world.localUser` and `world.localPeer` via `createUser` + `createPeer({ asLocal: true })`, so the defaults work for everything afterwards.

User and Peer entities anchor the recursion:

- `User` is **self-owned** — `OwnedBy(self)`.
- `Peer` is owned by its user and **self-authoritative** — `OwnedBy(user) + AuthoritativeFor(self)`.

For non-networked entities — system caches, derived state, test scratch — use `createEntity` directly.

## OwnedBy

Provenance. Doesn't move:

```ts
import { createUser, getOwner } from '@connectionengine/core'

const alice = createUser(world, { did: 'did:key:z6Mk...', asLocal: true })
// `asLocal: true` sets world.localUser; subsequent spawnPrefab() calls default
// their owner to Alice.
```

Used for:

- Disconnect cleanup — when a user's last peer disconnects, every entity they own is swept (by owner-user, not by authority). Entities meant to outlive a user's session must not be owned by that user.
- Permission inference — "is this requester one of the owner's peers?" → grants are common.
- Display — "made by Alice" UX.

You don't change `OwnedBy`. It's set on creation and stays. Transferring ownership is a different gesture (a delete + recreate, or an explicit transfer-of-ownership event in your app's semantics).

## AuthoritativeFor

Authority. Does move:

```ts
import { createPeer, spawnPrefab, transferAuthority } from '@connectionengine/core'

const aliceDesktop = createPeer(world, { user: alice, peerId: 'desktop', asLocal: true })
const alicePhone   = createPeer(world, { user: alice, peerId: 'phone' })

const vehicle = spawnPrefab(world, 'vehicle:1', { authority: aliceDesktop })

// User picks up their phone, drops their laptop:
transferAuthority(world, vehicle, alicePhone)
```

Authority is exclusive — at most one peer holds it for an entity at any time. The relation is `exclusive: true`, so adding a new authoritative peer atomically removes the previous one.

## What "having authority" means

Connection Engine doesn't enforce authority on the `continuous` channel — there's no per-packet check that says "is this peer authoritative?" That would be too expensive at the simulation tick rate.

Instead, **authority is a property your systems consult**. The convention is:

```ts
defineSystem(world, {
  name: 'PhysicsStep',
  phase: 'Simulation',
  execute: (world, dt) => {
    for (const e of physicsQuery(world)) {
      if (getAuthority(world, e) !== world.localPeer) continue
      // ...integrate physics, write to Transform...
    }
  }
})
```

The local peer steps physics for entities it has authority over. Other peers receive the resulting binary packets and write into their SoA stores without running physics themselves. State stays convergent because exactly one peer is the source of truth at a time.

This is also why **runtime binary packets aren't signed** — authority is structural, not cryptographic. If a non-authoritative peer were to inject a binary packet for an entity it doesn't own, every other peer's authoritative peer for that entity would overwrite it on the next tick. The lie gets corrected automatically.

## Authority transfer — gated end-to-end

Transfers are **gated on both sides**. The local check prevents accidentally authoring a transfer that won't be accepted; the receive-side check prevents any peer's local state from diverging when a forged or stale transfer arrives.

**Sender-side** (`transferAuthority` / `setAuthority`): throws if `canChangeAuthority(world, entity)` is false. The local peer has standing iff it's the current authority holder OR a peer of the entity's owner-user.

**Receive-side** (`applyAuthoredEnvelope` in `network/mutation.ts`): for every incoming `AuthoritativeFor` mutation, calls the standing check from `network/authority.ts` inline. The event's `author` DID must match either:

- The owner-user's DID — any of the owner's peers can authorise.
- The current authority's user DID — the running host can pass the torch (this is what host migration uses).

If neither, the event is dropped without being applied or appended to the event log. The gate runs unconditionally — networks can't opt out.

For mid-session handoff (handing the car to your phone, host migration, etc.) the flow is:

1. Current authority pauses (stops writing the entity).
2. Authority transfer event ships and converges. The gate accepts because the author is the current holder (or the owner-user).
3. New authority resumes (starts writing the entity).

The brief window where nobody's writing is usually fine — receivers continue interpolating from the last good state. If it isn't fine (high-precision physics, fast motion), apply a fade or a brief authority-hold by exchanging extra control messages.

## Recovery on disconnect — automatic

When a peer drops, the lifecycle's `sweepDisconnectedPeer` runs `recoverAuthority` for every entity whose `AuthoritativeFor` targets the leaving peer. It picks the lowest-id remaining peer of the entity's owner-user; if no peer of the owner is locally known, it falls back to `world.localPeer` as a last-resort host-migration successor.

```ts
// You don't call this yourself — it runs on disconnect automatically.
// What it does, conceptually:
recoverAuthority(world, entity, disconnectedPeer)
//   → find lowest-id peer where parentOf[peer] === ownerUser, skipping the leaver
//   → setAuthority(world, entity, successor, { unchecked: true })
```

For this to work, the disconnect-side has to know which peer entity to recover from. That comes from the HELLO handshake: every connection carries the remote engine's DID and peerId, and the receiver materialises a local `User` + `Peer` entity (using the path the sender encoded, so a later authored-event replay for those same identities is deduplicated). The materialised peer entity is stored on `connection.peer`, which the sweep walks.

## Request / grant

Sometimes a non-owner-peer wants authority — a moderator picking up a stuck NPC, a co-op partner driving the host's vehicle. `requestAuthority(world, entity, requester)` returns a result shaped for your governance hook:

```ts
const result = await requestAuthority(world, vehicle, modPeer)
// → { status: 'granted' | 'denied' | 'pending', reason?: string }
```

The default policy: owner's user-peer auto-grants; everyone else denies; an owner-less entity is treated as an invariant violation and denied (this should never happen — every entity gets an owner at creation). Higher layers (governance constraints, app-specific rules) can interpose by gating before the request reaches this default.
