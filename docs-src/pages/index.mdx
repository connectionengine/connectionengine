# Connection Engine

**Connection Engine is a TypeScript engine for real-time spatial experiences with a semantic, multiplayer-first foundation.** The runtime ECS holds a live graph of signed events. That graph has the same shape as the decentralised semantic web. The world your users move through and the data they share are therefore the same structure.

Game-engine developers will recognise the ECS pattern: bitECS, with schema-tagged components. Semantic-web and RDF developers will recognise the shape: `(entity, predicate, value)` triples with cryptographic provenance. Connection Engine is both.

## The thesis

Existing spatial multiplayer engines assume that their data lives inside their world. A transform belongs to an actor. An inventory belongs to a player. Scores belong to a save file. The world is a closed box, and you write code against it.

Existing semantic web stacks assume that their data lives outside any single app. Triples sit on a server somewhere, queryable, signed, and portable. The data is the substrate, and apps are views on it.

Connection Engine treats these as one architecture, by letting the ECS *be* the semantic graph. A component set on an entity is a triple. A relation between entities is a triple. An authored mutation is a signed event. A snapshot is a graph dump. Multiplayer convergence is event-sourcing.

Once you accept that equivalence, four layers you would otherwise write collapse into one:

- Components **are** the wire schema, so the ECS needs no networking layer bolted beside it.
- The event log **is** the durable form, so there is no separate persistence layer.
- The data already forms a semantic graph, so DIDs and signed events fit without a separate identity system.
- One component model drives logic, replication, and validation, so there is no scripting language to embed.

## What you get

- **bitECS-based runtime** with schema-driven components (TypeBox). Hot fields (Vec3, Quat, Float32, …) use structure-of-arrays storage.
- **Two replication channels** that share one schema. One rule splits them — *existence is governed, values are governed only where they are discrete*:
  - **`event`** — reliable, event-sourced, governance-validated. Use it for spawns, deletes, ownership transfers, and anything causal.
  - **`continuous`** — binary, per-field delta encoding, per-peer shadow maps. Use it for transforms, velocities, and anything driven at the simulation tick rate.
  - A component can hold both. Its existence is governed either way. Its continuous fields skip the gate, and systems constrain them instead.
- **Event-sourced late join** — a new peer replays the host's signed event log, which is idempotent on top of itself. A channel-agnostic state snapshot then advances continuous values from their creation pose to the present.
- **Three runtime modes** that share the same core:
  - **Solo** — anonymous agent, no transport, runs offline.
  - **Local** — `@connectionengine/local` adds Ed25519 / ZCAP / `did:key` signing.
  - **AD4M** — `@connectionengine/ad4m-bridge` wraps a running [AD4M](https://github.com/coasys/ad4m) instance as the agent, the transport, and the persistence layer.
- **Governance constraints as data** — a rule is an ECS entity that replicates like any other data, and each peer enforces it locally. Core supplies the registry and the gate; you register the kinds your application needs.

## What it is not (yet)

The current scope covers the **ECS + real-time transport foundation**. The higher layers have specifications, and we deferred them on purpose:

- No spatial layer yet — no transforms, WebXR, zones, or bounding trees. Components stay domain-agnostic at the moment.
- No renderer. The engine does not draw. It manages the data that the renderer reads.
- No high-frequency authoring or persistence beyond the event log itself.
- No WebRTC or WebSocket transports yet. Only the in-memory test transport and the AD4M-perspective transport work today.

What sits underneath them all does work: the ECS, the schema model, the mutation pipeline, the binary wire, the session protocol, identity, authority, and governance.
