# Vision & Convergence

## Why this exists

The web has no spatial layer. It has rectangles inside rectangles, document-shaped and query-fetched. When somebody wants something spatial — a 3D world, a multiplayer experience, a virtual venue — they build it as a closed silo, with their own assets, identity, data, and backend. Every spatial experience reinvents the stack from the glass to the physics.

In parallel, the **decentralised semantic web** has matured: RDF, SHACL, DIDs, VCs, and ZCAP-LD. [AD4M](https://github.com/coasys/ad4m) showed that an *agent-centric* spanning layer, in which users own their data and apps subscribe to it, is buildable today on Holochain. [WE](https://github.com/coasys/we) extends that into a frame-shaped social runtime, with shared Perspectives, Languages, and Neighbourhoods.

Connection Engine bets that **these two trajectories converge**. The data shape behind a multiplayer world — entities, components, relations, events — is structurally isomorphic to the data shape behind a decentralised semantic graph — subjects, predicates, objects, signed claims. Let the ECS BE the graph, and one runtime covers both jobs.

That runtime should look like a game engine to game developers, and like a semantic web stack to web standards people. Same data, two views.

## The convergence path

The plan, in outline:

**Stage 1 — Now.** Connection Engine exists as a TypeScript ECS and transport foundation. The three runtime modes — solo, local, and AD4M — prove that the core stays identity-agnostic. AD4M mode demonstrates that an existing Perspective can serve as the wire.

**Stage 2 — Spatial layer.** A Connection Engine application looks like a spatial scene, with transforms, WebXR sessions, zones, and bounding trees. One ECS hosts both the data and the spatial structure. At this stage the engine becomes useful for real experiences.

**Stage 3 — Connection Engine inside WE.** WE Frames host Connection Engine scenes the way they host other Frames today. The Perspective of a Frame becomes the wire for the scene, and the entities of the scene **are** the Expressions of that Perspective. Users move between spatial Frames the way they move between document-shaped Frames now.

**Stage 4 — Bundled with WE.** Connection Engine becomes the spatial runtime that WE distributes. The two stop being separate projects.

Once you accept the convergence, this is the obvious shape. Most of the work goes into keeping the engine small, avoiding hardcoded assumptions that WE will need to override, and respecting the design choices that AD4M has already made.

## The Living Web

Connection Engine also converges with [HexaField/w3c-living-web-proposals](https://github.com/HexaField/w3c-living-web-proposals), a set of W3C-style proposals. They aim to make these primitives part of the web platform itself, rather than an ecosystem choice: distributed identity, signed semantic mutations, agent-centric graph storage, and capability-based authorisation. Connection Engine sits on the same primitives.

If those proposals land in browsers, much of the work that `@connectionengine/local` and `@connectionengine/ad4m-bridge` do becomes redundant, because the browser will provide it directly. That would be a good day, and it should not require a hard refactor. Use web standards where they exist, and put compatibility shims (the `@living-web/*` polyfills) underneath where they do not.

## Why now

Two conditions make 2026 the right window:

1. **The web platform finally has the capabilities.** Browsers now have WebGPU, WebXR, and SharedArrayBuffer with Atomics for physics. `RTCDataChannel` works reliably. The web can host a spatial engine without native bridges.
2. **The decentralised stack is finally usable.** AD4M runs in production, the [WE](https://github.com/coasys/we) Frame model has demos, and Holochain has matured. The substrate exists. A credible spatial layer on top is what remains missing.

Nobody has yet defined what spatial-as-a-web-primitive looks like. Connection Engine is one attempt at it.

## How to follow the work

- This repository — `github.com/connectionengine/connectionengine`. Issues and PRs are welcome. The ECS and the network layer are stable enough to build on.
- [AD4M](https://github.com/coasys/ad4m) — the identity and transport substrate that Connection Engine targets.
- [WE](https://github.com/coasys/we) — the Frame runtime that Connection Engine aims to converge with.
- [Living Web proposals](https://github.com/HexaField/w3c-living-web-proposals) — the W3C-shaped attempt to make these primitives standard.
