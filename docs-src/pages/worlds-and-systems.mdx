# Worlds & Systems

## A world is a virtual scope inside an Engine

The ECS runs on the [Engine](/engine): bitECS storage, per-component storage, time, systems. Identity caches (`nameCache`, `uidOf`, `parentOf`) live as per-engine WeakMaps on the `UIDComponent` / `BelongsTo` definitions. Everything that's "ECS" is engine-wide. A `World` is a virtual scope on top — its own `worldRoot` entity that anchors a `BelongsTo` subtree, its own network state (the `networks` map, the authored queue, the event log, the runtime-dirty set), and the local identity for that scope (`localAgent`, `localUser`, `localPeer`).

```ts
import { createWorld, destroyWorld, createAnonAgent } from '@connectionengine/core'

const world = createWorld({
  engine: createEngine(),         // required. ECS runtime container.
  agent: createAnonAgent(),       // required. Local identity for this world.
})

// ...

destroyWorld(world) // closes networks, drops the worldRoot. Entities under it survive on the engine.
```

The `agent` is the only required option besides `engine`. There is no ambient engine; every call to `createWorld` takes an explicit `engine` built via `createEngine({ fixedTimeStep?, clock? })`.

A few things worth internalising:

- **Entity IDs are engine-wide.** Two worlds sharing an engine see the same ID space. Per-world iteration walks the `BelongsTo` tree from `worldRoot`.
- **The world's `worldRoot`** is a sentinel entity. Top-level named entities (created via `spawnPrefab`) bucket their UIDs under `world.worldRoot` in the engine's name cache. You use it occasionally — e.g. `getEntityByUID(world, world.worldRoot, 'scene:main')`.
- **The event log is per-world, canonical.** Networks are sync topology; they don't have their own histories. See [Peers & Sessions](/networking).
- **Spinning up isolated worlds is cheap.** Tests routinely create two and wire them with `connectInMemory` to simulate two peers in microseconds — each defaults to its own engine, so storage stays clean between tests.

## Time has two scales

Time lives on the engine, not the world. Per frame, the engine advances on two scales:

- **Variable step** — for `Input`, `Animation`, `Render` phases. The exact wall-clock delta since the last frame.
- **Fixed step** — for `Simulation` phase. Always exactly `engine.fixedTimeStep` seconds. The frame loop may run zero, one, or many simulation substeps depending on the variable delta — the accumulator pattern.

This is the same dual-rate trick most game engines use, and for the same reason: physics + game logic want determinism; rendering + input want frame-tight responsiveness.

`tickEngine(engine, deltaSeconds, { fixed, variable })` is the low-level primitive. `runSystems(world, deltaSeconds)` is the convenience wrapper that runs every system registered against `world.engine` in its phase. It does NOT flush networking — the driver does that explicitly (see "Driving a frame" below).

## Systems

A system is a phase-scoped function the scheduler runs every tick. You define them per-world:

```ts
import { defineSystem } from '@connectionengine/core'

defineSystem(world, {
  name: 'ApplyVelocity',
  phase: 'Simulation', // runs at fixed dt
  execute: (world, dt) => {
    for (const e of velocityQuery(world)) {
      // ...
    }
  }
})

defineSystem(world, {
  name: 'RenderAvatars',
  phase: 'Render', // runs at variable dt
  execute: (world, dt) => {
    // ...
  }
})
```

Four phases run in this order each frame:

```
Input (variable) → Simulation (fixed, may repeat) → Animation (variable) → Render (variable)
```

`runSystems` is pure ECS: it runs each phase, period. Networking is layered on top — the driver (runtime mode, test harness, application tick loop) calls `flushAuthored` + `flushRuntime` from `network/mutation` after `runSystems` returns:

```ts
import { runSystems, flushAuthored, flushRuntime } from '@connectionengine/core'

// One frame
runSystems(world, dt)
flushAuthored(world)  // authored first — receivers see new entities before binary packets reference them
flushRuntime(world)   // then the binary delta
```

Coalescing the flush at frame end means a frame's writes ship as a single outbound packet per channel per peer, rather than racing as systems execute. Authored before runtime so new entities are addressable on the receiver before the SoA payloads reference them.

## Ordering systems

If system order matters within a phase, use `before` / `after`:

```ts
defineSystem(world, {
  name: 'Damage',
  phase: 'Simulation',
  before: ['ApplyHealing'],
  execute: (world, dt) => { /* ... */ }
})
```

The scheduler topologically sorts each phase. Cycles fall back to insertion order. You can also `reorderSystem(world, handle, { before, after })` to change ordering at runtime.

## Reactors

Each system can optionally have a `reactor` — a DOMless Solid component (logic only) mounted via `createRoot` at registration:

```ts
defineSystem(world, {
  name: 'PresenceCounter',
  phase: 'Render',
  reactor: () => {
    const peers = useTrackedPeers()
    createEffect(() => console.log(`peers: ${peers().length}`))
  }
})
```

Reactors are useful for systems whose work is "react to changes" rather than "iterate entities" — UI bindings, telemetry, anything that wants Solid's signal graph. The reactor is disposed when the system is removed or the world is destroyed.

If you don't need reactivity, just provide `execute` and skip `reactor`.

## Injecting and removing

Systems are values you can move around:

```ts
const handle = defineSystem(world, { name: 'Foo', phase: 'Render', execute: ... })
removeSystem(world, handle)
// later:
injectSystem(world, handle) // re-attach + re-mount reactor
```

This matters for plugin systems and hot-reload flows: keep a `SystemHandle` reference, detach during reload, re-inject after. The reactor gets a fresh `createRoot` each time it's injected.
