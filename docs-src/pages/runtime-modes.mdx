# Solo, Local, AD4M

The same `@connectionengine/core` runs in three increasingly-integrated modes. You pick one at the edge of your app. Core doesn't care.

## Solo

No identity. No transport. Single world running in one process.

```ts
import { createWorld, createAnonAgent } from '@connectionengine/core'

const world = createWorld({ agent: createAnonAgent() })
```

`createAnonAgent()` returns `{ did: 'did:anon:abc123' }` — an opaque, unsignable identity. Useful for:

- Single-player games or tools.
- Offline-first apps that haven't introduced multi-user yet.
- Tests of pure ECS / engine logic, no network involved.
- Prototyping — you can build the whole component graph + system logic without ever thinking about peers, then bolt on a real identity later.

There's nothing different about a solo world. It has a full mutation pipeline, full event log, full governance support. It just never publishes outbound because there are no connections to publish to.

## Local (`@connectionengine/local`)

Real Ed25519 identity, signed authored events, capability-based authorisation, in-memory transport with signing.

```ts
import { createLocalAgent } from '@connectionengine/local'
import { createWorld } from '@connectionengine/core'

const alice = createLocalAgent({ seed: 'alice' })
// → { did: 'did:key:z6Mk...', keyPair: { publicKey, privateKey }, sign }

const world = createWorld({ agent: alice })
```

A `LocalAgent` has a real `sign` hook. When `connectLocalInMemory(worldA, worldB)` is used, every outbound authored event is signed with the local keypair; inbound events are verified against the event's `author` DID before apply. Tampered events emit `mutation.reject` with reason `'signature'`.

Use Local mode when:

- You want real cryptographic identity (`did:key:z6Mk...`) without a backing service.
- You're building a peer-to-peer app where each user holds their own keys.
- You want ZCAP capability chains for delegated authorisation. `addCapabilityConstraint(world, scope, cap)` attaches a capability that the registered `capability` constraint kind enforces.

Local mode is the simplest way to ship a real multi-user app without infrastructure dependencies. Stack a WebRTC `TransportEndpoint` on top and you have a P2P app with verified events.

## AD4M (`@connectionengine/ad4m-bridge`)

Identity, transport, and persistence all come from a running [AD4M](https://github.com/coasys/ad4m) instance. Authored events become AD4M Links inside a Perspective.

```ts
import { Ad4mClient } from '@coasys/ad4m'
import { createAd4mAgent, connectAd4m } from '@connectionengine/ad4m-bridge'
import { createWorld } from '@connectionengine/core'

const ad4m = new Ad4mClient(/* ... */)
const agent = await createAd4mAgent(ad4m)
const world = createWorld({ agent })

const perspective = await ad4m.perspective.get('uuid:...')
await connectAd4m(world, perspective)
```

Now every authored mutation in `world` is replicated as a Link in the Perspective. Every Link added by another agent in the Neighbourhood materialises as an authored event in `world`. The Perspective IS the wire and the persistence store.

Use AD4M mode when:

- You want a peer-to-peer app with **persistence handled for you** — AD4M's Languages back the Perspective with Holochain (or whatever Language the Perspective uses).
- You want to interoperate with other AD4M apps that share the same Perspective. A different app's view over the same Neighbourhood sees your entities as Links.
- You're building toward the [convergence path](/vision) — Connection Engine running as the spatial layer inside [WE](https://github.com/coasys/we).

The runtime binary channel doesn't go through AD4M (it's too high-frequency for Link-based storage). Authored channel uses AD4M; runtime uses whatever direct transport you've wired alongside (typically WebRTC).

## Switching modes

Because the only thing core knows about identity is the `Agent` interface — `{ did: string; sign?: ... }` — switching modes is a one-line change at the call site that creates the world. Everything else stays the same.

```ts
// Solo:
createWorld({ agent: createAnonAgent() })

// Local:
createWorld({ agent: createLocalAgent({ seed: 'alice' }) })

// AD4M:
createWorld({ agent: await createAd4mAgent(ad4mClient) })
```

This is intentional. The three-mode design lets you start solo for prototyping, move to local once you have multi-user requirements, and graduate to AD4M when you want decentralised persistence and ecosystem interop — without rewriting your component schemas, your systems, your governance, or anything else.

## What the modes don't change

- **The schema model.** Same `defineComponent` definitions across all three.
- **The mutation pipeline.** Same authored + runtime split.
- **Governance.** Same constraint registry; Local adds `capability`, AD4M adds its own kinds.
- **Late join.** Same event-sourced replay protocol over whichever transport.
- **Authority & ownership.** Same `OwnedBy` / `AuthoritativeFor` semantics.

The modes change WHO signs your events, WHERE bytes go, and WHO stores them — not the data model your app is built on.
