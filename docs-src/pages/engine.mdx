# Engine

An **Engine** is the global runtime container. One per process (almost always). Anything truly global to a Connection Engine runtime lives here:

- **One bitECS world.** All entities allocated in this engine share an ID space. CE Worlds scope themselves to subtrees inside it.
- **Component / relation type registries.** `defineComponent({ id: 'Foo', ... })` registers `Foo` on the engine and dedups by id.
- **Per-component storage.** SoA typed arrays live directly on each `ComponentDefinition` (so `Transform.position.x[eid]` works without any lookup). Per-entity instance maps for value fields live on the engine, keyed by component + entity.
- **The `ComponentSchema` registry.** Shareable replication metadata (`{ id, jsonSchema, shaclShape, channel }`).
- **`customRegistries`.** An open slot where higher layers stamp their own engine-keyed state (e.g. `network/peers.ts` keeps the per-engine `PeerTransportRegistry` here).

CE Worlds are NOT engines. A World is a logical scope inside an engine — see [Worlds & Systems](/worlds-and-systems).

## Ambient default

You don't usually create an Engine explicitly. The ambient default is created lazily on first use:

```ts
import { defineComponent, createWorld, createAnonAgent } from '@connectionengine/core'

// Both register against the same ambient engine.
const Health = defineComponent({ id: 'Health', schema: /* ... */ })

// World is allocated in the ambient engine too.
const world = createWorld({ agent: createAnonAgent() })
```

The ambient engine is fine for almost everything. Multiple worlds inside it share the type registries and the bitECS storage; world membership is tracked via `world.entities` and the `BelongsTo` chain rooted at `world.worldRoot`.

## When to create your own

`createEngine()` returns a fresh isolated engine. Reasons to use it:

- **Test isolation.** A test that wants its own component registry without polluting the ambient one.
- **Plugin sandboxes.** A dynamically-loaded plugin that should run inside its own bitECS world.
- **Multi-tenant server.** Hosting multiple unrelated worlds where you don't want entity IDs to cross over.

```ts
import { createEngine, defineComponent, createWorld } from '@connectionengine/core'

const engine = createEngine()
const Score = defineComponent({ id: 'Score', schema: /* ... */, engine })
const world = createWorld({ agent: /* ... */, engine })
```

Note that components defined on different engines are *different definitions* — `defineComponent({ id: 'Foo', engine: A })` and `defineComponent({ id: 'Foo', engine: B })` give you two distinct `ComponentDefinition` objects with disjoint storage.

## Peer transport dedup

Engine-level state that the network layer adds: a `PeerTransportRegistry` that ensures only one physical transport (RTCPeerConnection / QUIC connection / WebSocket / in-memory pair) exists per remote DID, even when multiple Networks address the same peer.

```ts
import { getPeerRegistry } from '@connectionengine/core'

const peers = getPeerRegistry(world.engine)
const handle = peers.acquire('did:key:z6Mk...', () => createWebRTCTransport(/* ... */))
// handle.endpoint — the shared transport
// handle.release() — refcount decrement
```

Each Network on each World requests transports via the registry rather than opening its own. This becomes meaningful when WebRTC lands: one peer connection multiplexes voice + gameplay + admin channels rather than negotiating each separately.

## What's on the engine — at a glance

```ts
interface Engine {
  readonly bitECS: bitecs.World                                // entity ID space
  readonly components: Map<string, ComponentDefinition>        // id → def
  readonly componentsByRef: WeakMap<...>                       // bitECS ref → def
  readonly componentStores: WeakMap<...>                       // per-(component, entity) instance + view bags
                                                               // (SoA arrays live on the definition itself)
  readonly relations: Map<string, RelationDefinition>          // name → def
  readonly relationsByRef: WeakMap<...>
  readonly schemas: Map<string, ComponentSchema>               // replication metadata
  readonly customRegistries: Map<symbol, unknown>              // peer registry + future plugins
}
```

You almost never touch these fields directly. Most engine state is accessed through `defineComponent`, `defineRelation`, `getComponentById(id, engine)`, etc. The fields are public so plugin code and tooling can introspect.
