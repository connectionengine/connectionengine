# Architecture at a Glance

Connection Engine has three nested scopes:

```
Engine (per-app ECS runtime container; createWorld({ engine, agent }) — always explicit)
│
├── bitECS storage (entity ID space, archetype tables)
├── componentStores (per-engine instance + view bags, keyed by ComponentDefinition)
├── time, clock (engine-wide simulation)
│
└── World (many per engine — virtual hierarchy + network scopes)
    │
    ├── worldRoot (sentinel entity; anchors this world's BelongsTo subtree)
    ├── localAgent / localUser / localPeer (local identity for this scope)
    ├── eventLog (canonical history for this world — networks are sync topology, not data space)
    ├── authoredQueue / runtimeDirty (per-world mutation pipeline state)
    │
    └── Networks (many per world — sync topology)
        ├── connections (peer connections on this network)
        ├── publishAuthored / publishRuntime hooks
        └── validateAuthored governance gate
```

Component and Relation **definitions** are module-level globals — `defineComponent({ id })` produces one `ComponentDefinition` shared across every engine. Per-engine *storage* lives in `engine.componentStores`; the **identity caches** (`nameCache`, `uidOf`, `parentOf`) live as typed `WeakMap<Engine, …>` extension properties on `UIDComponent` / `BelongsTo` — global definition, per-engine state.

Three rules govern the dependency graph:

1. **`Engine` owns the ECS.** bitECS storage, per-component storage, time, systems. Every `createWorld` takes an explicit `engine`. One engine per app is the dominant production shape; tests give each peer its own.
2. **`World` is a virtual scope.** A `worldRoot` entity anchoring a subtree, plus the per-world network state (event log, authored queue, runtime-dirty, networks) and the local identity for that scope.
3. **`Network` is many per world.** Sync topology — different networks ship the same events through different connections. Spatial segmentation, voice / video, admin overlays.

The on-disk layout follows the conceptual split:

```
@connectionengine/core
├── schema/    — TypeBox + SoA tag kinds (Vec3, Quat, ArrayBuffer, …)
├── maths/     — Vec/Quat structure-of-arrays types
├── ecs/       — Engine, World, Entity, Component, Relation, Observer,
│                Identity (UID + BelongsTo), Query, System scheduler, Prefab
│                — everything local-runtime
└── network/   — Mutation pipeline (authored queue + event log + flush + apply),
                 Transport, Lifecycle, Binary codec, Snapshot,
                 User / Peer, Authority, Governance, Peers registry
                 — everything that exists because state is distributed
```

Layering enforced mechanically by oxlint:

- **`ecs/`** is foundational. It does not know about authoring, replication, peers, or governance. No imports from `network/`.
- **`network/`** is the distribution layer. May import anything in `ecs/`. The mutation pipeline lives here, not in some middle layer — the event log, `flushAuthored`, `applyAuthoredEnvelope`, the authority gate are all networking-flavoured concepts. There's no scenario where they exist without distribution.

Identity (`UIDComponent` + `BelongsTo`) lives in `ecs/` because entity addressing is foundational, not a wire concern. The `Network` *type* lives in `ecs/world.ts` so the `World` interface can name the field it carries; the *construction helpers* (`addNetwork`, `ensureDefaultNetwork`) and the pipeline that drives it all live in `network/`.

The receive-side authority gate is a direct named call from `network/mutation.ts` into `network/authority.ts` — both in the same layer. No runtime registration, no hook pattern.

## The two adapter packages

Both compose with core — they don't fork it.

**`@connectionengine/local`** adds:
- Ed25519 keypairs + `did:key` agents
- ZCAP-LD capability chains
- A `capability` governance constraint registered with core's constraint registry
- A signing in-memory transport (`connectLocalInMemory`)

**`@connectionengine/ad4m-bridge`** adds:
- An `Ad4mAgent` that wraps a running AD4M instance's `Ad4mClient.agent`
- A transport that encodes authored events as AD4M Links inside a Perspective
- Lifecycle plumbing that subscribes to Perspective changes for inbound

A consumer picks one (or none) at the edge. Core itself stays identity- and crypto-agnostic — its `Agent` interface is just `{ did: string; sign?: (bytes) => Uint8Array | Promise<Uint8Array> }`.

## The two replication channels

The single most important mental model in Connection Engine. Every component lands on exactly one **replication channel**, derived from its schema at definition time. The channel decides everything about how the component travels.

| `channel`     | Wire shape                       | Cadence       | Use for                                 |
|---------------|----------------------------------|---------------|-----------------------------------------|
| `event`       | Authored envelope (JSON-shaped)  | Per-event     | Spawns, ownership, governance, intent   |
| `continuous`  | Binary delta, per-field mask     | Per-tick      | Transforms, velocities, anything at the simulation tick rate |
| `local`       | Never replicated                 | n/a           | Caches, view-state, machine-local data  |

The channel is **derived from the schema**. Any SoA-tagged field (Vec3, Quat, Float32, …) puts the component on `continuous`; anything else lands on `event`. `defineComponent({ sync: false })` forces `local`.

Mixing SoA and non-SoA fields in one component throws at definition time. You split into two components — one continuous, one event — because they have different replication contracts. See [Components](/components) for the rationale.

## Mutation routing across networks

A write to a component on an entity goes to the world's event log (for `event` channel) or marks the entity dirty (for `continuous` channel). At flush time the mutation pipeline runs `routeNetworks(world, entity)` to decide which networks receive the mutation. Today this is a hardcoded broadcast-to-all; tomorrow, a spatial layer will replace it with proximity-based routing without touching `mutation.ts`.

Same event log; many sync topologies on top.

## The session protocol

Two peers connect over a `TransportEndpoint` (dual-channel: `events` for reliable control + authored envelopes, `stream` for binary `ArrayBuffer` packets). The lifecycle layer wraps the endpoint as a `Connection`, attaches it to a Network on the local World, and runs a four-step session:

```
1. HELLO    — exchange { agentDID, knownEventCount, networkId bindings }
2. SNAPSHOT — full state baseline: every named entity, all components, every channel
3. REPLAY   — host streams authored events from joiner's cursor (idempotent)
4. LIVE     — both sides forward authored envelopes + binary runtime packets
```

Late join is **event-sourced for authored state**: the joiner replays signed events to catch up. Each event has a composite signature, and `appendEventLog` is idempotent on that signature, so the same event delivered twice is dropped silently.

Continuous-channel components have no event-log representation, so replay cannot bootstrap them — and the binary channel only ships entities that are currently dirty, which leaves an entity at rest permanently invisible to a late joiner. The SNAPSHOT step covers that gap with a channel-agnostic baseline, applied with `origin: 'network'` so it never echoes back. See [Peers & Sessions](/networking).

## Identity is a path

Entities have integer IDs allocated from the engine's bitECS world — globally unique within an engine, but meaningless across processes. **Entity identity on the wire is a UID path** — a list of strings walking the `BelongsTo` chain from a world's `worldRoot`.

```
['scene:main', 'avatar:alice'] → entity 42 on world A
['scene:main', 'avatar:alice'] → entity 17 on world B
```

The path is what travels. Receivers look it up (or create the chain on demand) in their own world. This is also how the semantic graph view emerges — every path is a stable URI other events can reference.

For the `continuous` channel, paths would be too verbose, so each connection maintains a `NetworkIdTable` — a compact `u32` mapping exchanged at handshake and updated lazily as new entities appear.
