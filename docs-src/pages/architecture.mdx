# Architecture at a Glance

Connection Engine is one core package and two adapter packages, organised by domain rather than by tier:

```
@connectionengine/core
├── schema/    — TypeBox + SoA tag kinds (Vec3, Quat, ArrayBuffer, …)
├── maths/     — Vec/Quat structure-of-arrays types
├── ecs/       — World, Entity, Component, Relation, Observer, Identity, Query
├── engine/    — System scheduler, Mutation pipeline, Prefab
└── network/   — Transport, Lifecycle, Binary codec, Snapshot, Peer,
                Authority, Governance, Compression
```

Three rules govern the dependency graph, and oxlint enforces them mechanically:

1. **`ecs/` is the foundation.** It must not import from `engine/` or `network/`.
2. **`engine/` may depend on `ecs/`** but not on `network/`.
3. **`network/` may depend on both**, since wire-format concerns sit on top.

That's why, for example, identity (`UIDComponent` + `BelongsTo`) lives in `ecs/` even though peers and DIDs feel network-ish — entity addressing is foundational to how the ECS works, not a wire concern. Conversely, snapshot serialisation lives in `network/snapshot.ts` because it's how state crosses a wire, even though it walks ECS structures.

## The two adapter packages

Both packages compose with core — they don't fork it.

**`@connectionengine/local`** adds:
- Ed25519 keypairs + `did:key` agents
- ZCAP-LD capability chains
- A `capability` governance constraint registered with core's constraint registry
- A signing in-memory transport (`connectLocalInMemory`)

**`@connectionengine/ad4m-bridge`** adds:
- An `Ad4mAgent` that wraps a running AD4M instance's `Ad4mClient.agent`
- A transport that encodes authored events as AD4M Links inside a Perspective
- Lifecycle plumbing that subscribes to Perspective changes for inbound

A consumer chooses one (or none) at the edge. Core itself remains identity- and crypto-agnostic — its `Agent` interface is just `{ did: string; sign?: (bytes) => Uint8Array | Promise<Uint8Array> }`.

## The two replication channels

This is the single most important mental model in Connection Engine. Every component lands on exactly one **replication channel**, derived from its schema at definition time. The channel decides everything about how the component travels.

| `channel`     | Wire shape                       | Cadence       | Use for                                 |
|---------------|----------------------------------|---------------|-----------------------------------------|
| `event`       | Authored envelope (JSON-shaped)  | Per-event     | Spawns, ownership, governance, intent   |
| `continuous`  | Binary delta, per-field mask     | Per-tick      | Transforms, velocities, anything at the simulation tick rate |
| `local`       | Never replicated                 | n/a           | Caches, view-state, machine-local data  |

The channel is **derived from the schema** — there is no `mutationCategory` enum to set. Any SoA-tagged field (Vec3, Quat, Float32, …) puts the component on `continuous`; anything else lands on `event`. The only opt-out is `defineComponent({ sync: false })`, which forces `local`.

Mixing SoA and non-SoA fields in one component throws at definition time. You split into two components — one continuous, one event — because they have different replication contracts. See [Components](/components) for the rationale.

## The session protocol

Two peers connect over a `TransportEndpoint` (the abstraction over WebRTC / WebSocket / in-memory). The lifecycle layer wraps the endpoint as a `Connection` and runs a three-step session:

```
1. HELLO    — exchange { agentDID, knownEventCount, networkId bindings }
2. REPLAY   — host streams authored events from joiner's cursor (idempotent)
3. LIVE     — both sides forward authored envelopes + binary runtime packets
```

Late join is **purely event-sourced**. There is no snapshot in the join protocol — the joiner brings itself up to date by replaying signed events. Each event has a composite signature, and `appendEventLog` is idempotent on that signature, so the same event delivered twice is dropped silently. Two peers reconnecting after a long disconnect just send each other their missing events.

## Identity is a path

Entities have integer IDs internal to a world, but those IDs are meaningless across worlds. **Entity identity is a UID path** — a list of strings walking the `BelongsTo` chain from a root.

```
['scene:main', 'avatar:alice'] → entity 42 on world A
['scene:main', 'avatar:alice'] → entity 17 on world B
```

The path is what travels the wire. Receivers look it up (or create the chain on demand) in their own world. This is also how the semantic graph view emerges — every path is a stable URI you can refer to from other events.

For the high-frequency binary channel, paths would be too verbose, so there's a `NetworkIdTable` per connection — a compact `u32` mapping exchanged at handshake and updated lazily as new entities appear.
