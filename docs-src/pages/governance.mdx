# Governance

## Constraints are data

A "rule" in Connection Engine is not engine code. A rule is an entity that carries a constraint component and a `HasConstraint` relation, which points at a scope:

```ts
import { addConstraint } from '@connectionengine/core'

const scene = spawnPrefab(world, 'scene:guarded')
addConstraint(world, scene, 'max-health', { max: 100 })
```

Constraints are entities with authored components, so they replicate exactly like any other data. Every peer receives them through the normal mutation pipeline, and enforces them locally. There is no separate "config sync" channel. The rules **are** the data.

This makes governance composable. You can govern a scene, an inventory, or a single object. Constraints walk the `BelongsTo` chain, so anything inside a constrained scope inherits the rule.

## Core defines no constraint kinds

Which writes a world admits is an application question, so the engine takes no position on it. Core supplies the registry, the scope walk, and the enforcement. You supply the kinds.

```ts
import { defineConstraint, Schema } from '@connectionengine/core'

defineConstraint({
  kind: 'max-health',
  id: 'MaxHealthConstraint',
  schema: Schema.Object({ max: Schema.Number({ default: 0 }) }),
  validate({ event, data, violations }) {
    if (event.predicate !== 'Health') return
    const current = (event.value as { current?: number } | null)?.current
    if (typeof current === 'number' && current > (data.max as number)) {
      violations.push({ kind: 'max-health', reason: `${current} exceeds ${data.max}` })
    }
  }
})
```

`addConstraint(world, scope, 'max-health', { max: 100 })` now works. `resolveConstraints` collects the kind, and `validateEvent` runs it.

`@connectionengine/local` defines a `capability` kind the same way, for ZCAP-LD authorisation. It needs no fork of core, and neither does yours.

## Write `validate` as a pure function

A validator receives the event, the constraint configuration, and the guarded scope. Nothing else — no world handle, no clock, no callback into your application.

That signature is the point. Every peer holds the same constraint data and runs the same code, so every peer must reach the same verdict. A validator that read a local clock would let two peers judge the same event differently, a fraction of a second apart, and diverge with nothing to detect it. A validator that asked a local oracle would do the same.

When a rule needs a notion of "now", use `event.timestamp`. The author stamps it, so it reads the same on every peer.

## Engine-internal enforcement

Governance runs engine-internally. The mutation pipeline calls `validateEvent` directly — no pluggable callback, no gate field on the world:

`validateEvent` walks the scope hierarchy from the entity of the event, collects every applicable constraint, runs each kind, and returns `{ allowed, violations }`. Inbound `applyAuthoredEnvelope` calls it before it applies an event. A refused event neither applies nor enters the event log.

Governance runs on **received** events. Local writes pass through the authored queue and go out optimistically. Call `validateEvent` yourself before `setComponent` if you want to check a local write first.

## Resolving constraints

`resolveConstraints(world, entity)` walks `entity → BelongsTo parent → ... → root` and collects every constraint attached with `HasConstraint`. It returns the most specific first:

```ts
resolveConstraints(world, avatar)
// → [{ entity: 17, kind: 'max-health', data: { max: 100 }, scope: scene }]
```

Use it to answer "what governs this entity?" while debugging, or to show a user why a write was refused.

## What governance is NOT

- It is not a permissions API for local-only writes. Local mutations pass through the queue and go out. Mark the component `local` to keep a write inside this world — that is the tool for the job.
- It is not transport-level auth. Whether a peer may *connect* is a separate concern, and the transport handles it. Governance starts once a peer is already in the session.
- It is not authority enforcement. See [Authority & Ownership](/authority-and-ownership). Runtime authority is structural, and carries no signature.

Governance checks **authored events on apply**, and nowhere else.
