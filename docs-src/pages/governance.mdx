# Governance

## Constraints are data

A "rule" in Connection Engine is not engine code. A rule is an entity that carries a constraint component and a `HasConstraint` relation, which points at a scope:

```ts
import { addConstraint } from '@connectionengine/core'

const scene = spawnPrefab(world, 'scene:guarded')

addConstraint(world, scene, 'credential', {
  requiredCredential: 'builder',
  operations: ['modify']
})
```

Constraints are entities with authored components, so they replicate exactly like any other data. Every peer receives them through the normal mutation pipeline, and enforces them locally. There is no separate "config sync" channel. The rules **are** the data.

This design move makes governance composable. You can govern a scene, an inventory, or a single object. Constraints walk the `BelongsTo` chain, so anything inside a constrained scope inherits the rule.

## Built-in constraint kinds

Core includes three kinds. None of them needs a specific identity provider beyond an opaque DID string:

| Kind         | What it does                                                            |
|--------------|-------------------------------------------------------------------------|
| `credential` | Requires the event author to hold a named credential (oracle-supplied).  |
| `temporal`   | Rate-limits writes per author (min interval, max count per window).      |
| `content`    | Validates field shape — number ranges, string patterns, blocklists.      |

Install `@connectionengine/local` for ZCAP capability-based authorisation. That package registers a `capability` kind. `@connectionengine/ad4m-bridge` adds its own kind for AD4M-perspective-based rules.

## The validator gate

Set `network.validateAuthored` to attach a validator to a network. Each network on a world holds its own gate, so different networks can hold different rules:

```ts
import { ensureDefaultNetwork, validateEvent } from '@connectionengine/core'

const network = ensureDefaultNetwork(world)
network.validateAuthored = (event) =>
  validateEvent(world, event, {
    hasCredential: (did, cred) => myOracle.holds(did, cred)
  }).allowed
```

`validateEvent` walks the scope hierarchy from the entity of the event. It collects every applicable constraint, runs the `validate` function of each one, and returns `{ allowed, violations }`. Inbound `applyAuthoredEnvelope` consults the gate before it applies an event. It drops a failed event, and neither applies it nor appends it to the event log.

The gate runs on **received** events. Local writes pass through the authored queue, and the engine emits them optimistically. Call `validateEvent` yourself before `setComponent` if you want pre-commit validation of local writes. Letting the network enforce convergence is almost always cheaper. Peers reject bad writes on apply, and your own bad writes fail on the next round-trip review.

## The registry

The `credential`, `temporal`, and `content` kinds are not a hardcoded switch inside `validateEvent`. A registry holds them:

```ts
import { registerConstraintKind } from '@connectionengine/core'

registerConstraintKind({
  kind: 'my-custom-rule',
  component: MyCustomConstraintComponent,
  validate({ world, event, data, scope, context, violations }) {
    if (somethingIsWrong(event, data)) {
      violations.push({ kind: 'my-custom-rule', reason: '...' })
    }
  }
})
```

`addConstraint(world, scope, 'my-custom-rule', { ... })` now works. `resolveConstraints` collects the new kind, and `validateEvent` runs it. The engine needs no change.

`@connectionengine/local` adds the `capability` kind the same way, without a fork of core:

```ts
// in @connectionengine/local/src/governance.ts
registerConstraintKind({
  kind: 'capability',
  component: CapabilityConstraintComponent,
  validate({ world, event, data, context, violations }) {
    // ZCAP verification ...
  }
})
```

## Resolving constraints

`resolveConstraints(world, entity)` walks `entity → BelongsTo parent → ... → root`, and collects every constraint attached with `HasConstraint`. It returns the most specific constraint first, which is the one closest to the entity. Use it to debug the question "what governs this entity?":

```ts
import { resolveConstraints } from '@connectionengine/core'

resolveConstraints(world, avatar)
// → [{ entity: 17, kind: 'credential', data: { ... }, scope: scene }]
```

App code rarely calls this function. It serves engine-level governance, and it shows users why the engine rejected a write.

## What governance is NOT

- It is not a permissions API for local-only writes. Local mutations pass through the queue and go out. Mark the component `local` to keep a write inside this world — that is the tool for the job.
- It is not transport-level auth. Whether a peer may *connect* is a separate concern, and the transport handles it. Governance starts once a peer is already in the session.
- It is not authority enforcement. See [Authority & Ownership](/authority-and-ownership). Runtime authority is structural, and carries no signature.

Governance gates **authored events on apply**, and nowhere else.
