# Components

## A component is a schema

```ts
import { Schema, defineComponent } from '@connectionengine/core'

const Transform = defineComponent({
  id: 'Transform',
  schema: Schema.Object({
    position: Schema.Vec3(),
    rotation: Schema.Quat()
  })
})

const Health = defineComponent({
  id: 'Health',
  schema: Schema.Object({
    current: Schema.Number({ default: 100 }),
    max: Schema.Number({ default: 100 })
  })
})
```

Three things to internalise about `defineComponent`:

1. **Definitions are global.** `defineComponent({ id: 'Foo', ... })` registers a process-wide singleton keyed on `id` — calling it again with the same id returns the same definition. Per-engine storage lives in `engine.componentStores`; the definition itself is shared across every engine that uses it.

2. **SoA storage lives on the definition.** SoA-tagged fields (`Schema.Vec3`, `Schema.Quat`, `Schema.ArrayBuffer`, `Schema.SoAStore`) are spread directly as properties on the returned definition. `Transform.position` is a `Vec3SoA` — the same object you'd get from a bitECS-style `defineComponent({ position: { x: f32, y: f32, z: f32 } })`. There is no separate "stores" lookup; the definition *is* the store.

3. **The schema decides the wire.** SoA fields travel the binary `continuous` channel. Value-typed fields travel the authored `event` channel. The channel is *derived* from what's in your schema.

## Replication channels

Every component lands on exactly one channel, computed once at definition time. Three channels, one rule each:

| `$channel`    | Selected when                                | How it travels                                      |
|---------------|----------------------------------------------|-----------------------------------------------------|
| `continuous`  | Schema has any SoA-tagged field              | Binary delta, per-field change mask, per-peer shadow |
| `event`       | Schema has no SoA fields                     | Authored envelope, event-sourced, governance-validated, replayed on late join |
| `local`       | `defineComponent({ sync: false })`           | Never replicates                                     |

You don't pick the channel directly — you pick the schema, and `sync` for opt-out:

```ts
const Score = defineComponent({
  id: 'Score',
  // No SoA fields → `event` channel. No override needed.
  schema: Schema.Object({ points: Schema.Number({ default: 0 }) })
})

const RenderCache = defineComponent({
  id: 'RenderCache',
  sync: false, // pure derived state — don't ship
  schema: Schema.Object({ lastDrawTime: Schema.Number({ default: 0 }) })
})
```

## The `$`-prefixed meta surface

All metadata on the definition lives behind a `$` prefix so the bare keys are reserved for SoA stores spread from the schema:

- `Score.$id`              — component id (`'Score'`)
- `Score.$label`           — human label (defaults to `$id`)
- `Score.$schema`          — the TypeBox schema you passed in
- `Score.$sync`            — `true` unless explicitly opted out
- `Score.$channel`         — `'event' | 'continuous' | 'local'`
- `Score.$isBinary`        — `true` iff the component takes the binary path
- `Score.$componentSchema` — the shareable replication-metadata blob (jsonSchema + shaclShape + channel)
- `Score.$soaFields` / `Score.$valueFields` — field-name partitions used by the mutation pipeline

So for `Transform`:

```ts
Transform.$id           // 'Transform'
Transform.$channel      // 'continuous'
Transform.position      // Vec3SoA<Float32ArrayConstructor>
Transform.rotation      // QuatSoA<Float32ArrayConstructor>
```

The bare names (`position`, `rotation`) are reserved for *your* schema fields.

### Mixing SoA and non-SoA fields is an error

A component cannot have both. `defineComponent` throws at definition time:

```ts
defineComponent({
  id: 'TransformWithLabel',
  schema: Schema.Object({
    position: Schema.Vec3(),      // SoA
    label:    Schema.String()      // value-typed
  })
})
// → throws: components cannot mix SoA-tagged fields with value-typed fields.
//   Split into two components — SoA fields ship via the binary delta channel;
//   value-typed fields ship as authored events.
```

The split is `Transform { position, rotation }` and `Label { text }`. They're logically related but travel different channels with different semantics; making the developer split is the whole point of the strict check. The schema declares intent.

The reason this rule matters: **two components with identical-looking schemas can have very different network behaviour** depending on whether they hold SoA or value fields. A `Vec3 position` on a `Transform` is a binary stream at the simulation tick rate with last-write-wins semantics. A `Vec3` representing a spawn point should be expressed differently — as three numbers in an `event` component, or wrapped in a `SpawnConfig` that's authored — because changes to it are causally meaningful and belong in the event log.

## Reading and writing

```ts
import { setComponent, getComponent, hasComponent, removeComponent } from '@connectionengine/core'

setComponent(world, entity, Health, { current: 50 })
// → addComponent in bitECS, fills defaults, writes value fields to the
//   instance store, marks dirty (continuous) or queues authored event (event)

getComponent(world, entity, Health)
// → { current: 50, max: 100 }  — the live instance object

hasComponent(world, entity, Health) // → true

removeComponent(world, entity, Health)
// → bitECS removeComponent, drops instance, clears dirty flag,
//   queues authored remove event for `event`-channel components
```

## Two equally first-class read paths

For continuous components, you have two equally fast ways to read state. Pick the one that fits the system you're writing.

### 1. `Transform.position.x[eid]` — the bitECS-style hot path

SoA storage lives directly on the definition. The per-axis arrays are real `Float32Array`s, suitable for `gl.bufferData` GPU uploads and tight inner loops:

```ts
const positionX = Transform.position.x
const positionY = Transform.position.y
const positionZ = Transform.position.z

for (const eid of entities) {
  positionX[eid] += dt * velocityX[eid]
  positionY[eid] += dt * velocityY[eid]
  positionZ[eid] += dt * velocityZ[eid]
}
```

Zero indirection, zero per-call work. This is the path systems hit at 60 fps.

### 2. `getComponent(world, e, Transform).position.x` — the ergonomic path

Sometimes you want a named handle on a single entity's component:

```ts
const t = getComponent(world, e, Transform)
if (!t) return
t.position.x += dt * vx
t.position.y += dt * vy
console.log(`rotation: ${t.rotation.w}`)
```

Both paths read and write the same underlying SoA storage — no copies, no refresh. The view objects use property accessors (`Object.defineProperty` getters/setters) that delegate straight to the SoA arrays. Writes through either path are immediately visible to the other.

### Stable references, zero garbage on the hot path

`getComponent` returns a **stable JS object reference** for a given `(component, entity)` pair — calling it repeatedly returns the same object. The per-field view objects inside it (e.g. `t.position`, `t.rotation`) are also stable per entity:

```ts
const t1 = getComponent(world, entity, Transform)
const t2 = getComponent(world, entity, Transform)
t1 === t2                     // true
t1.position === t2.position   // true — same view, getter-backed
```

The two channels back this differently:

- **Event-channel components** (value fields): `getComponent` returns the engine's instance-store record for that entity directly. It IS the underlying data. `setComponent` mutates the same object.
- **Continuous-channel components** (SoA fields): `getComponent` returns a cached per-entity view bag whose fields are `SoA.view(entity)` projections. Each projection's `.x/.y/.z/.w` accessors read and write the underlying typed arrays. No refresh step, always live.

**Writing through the view works.** `t.position.x = 5` sets `Transform.position.x[entity] = 5`. But the mutation pipeline doesn't know about it on its own — for replicated state, call `setComponent` (or mark dirty explicitly) so the binary delta picks it up.

## The `{ origin }` option

Every mutating call accepts `{ origin: 'local' | 'network' }`:

```ts
setComponent(world, entity, Health, { current: 50 }, { origin: 'network' })
```

- `'local'` (default) means "this came from local code, replicate it." The mutation pipeline picks it up and ships it.
- `'network'` means "this came from a received envelope, do NOT re-broadcast." Otherwise envelopes would echo forever between peers.

You almost never write `origin: 'network'` yourself — the receive path (`applyAuthoredEnvelope`, the binary pipeline) does it for you. It's surfaced because it's central to the no-loop invariant: the receive side stamps `network`, the dirty-flag / authored-queue path skips anything stamped `network`.

## Defaults and `Value.Default`

The schema's `default: ...` is the source of truth. On first `setComponent`, the engine fills any field you didn't provide from the defaults via TypeBox's `Value.Default`. Subsequent `setComponent` calls do partial updates — only fields you provide are written.

This means it's safe to:

```ts
setComponent(world, e, Health, {}) // creates with current: 100, max: 100
setComponent(world, e, Health, { current: 25 }) // current: 25, max: 100
```

…which is a frequent pattern when receiving a binary-channel snapshot: the binary path calls `setComponent(world, entity, component, {})` to ensure bitECS presence, then the codec writes the actual SoA values directly into `component.position.x[entity]` and friends.

## When you have a lot of components

Components are cheap. Don't make them godlike. A `Stats` component with twenty fields is harder to reason about than five focused components — `Health`, `Mana`, `Stamina`, `Combat`, `Movement`. Smaller components also play better with queries: `query(world, [Health, Damaged])` is more selective than `query(world, [Stats])` plus a manual filter.

The exception is when fields move together at the same cadence — `position` and `rotation` on `Transform` belong together because they're written and replicated as one logical unit. Co-locate when behaviour is correlated; split when it isn't.
